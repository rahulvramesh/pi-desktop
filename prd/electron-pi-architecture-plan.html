i. Overview

This document describes the architecture for an Electron-based graphical client to the Pi coding agent. The client must work against the user's local codebase today and against remote machines (cloud dev boxes, VMs, sandboxes) over SSH in a later phase. The renderer code, IPC contract, and user-facing experience are the same in both cases.

The plan adopts both of Pi's programmatic surfaces — the SDK and RPC mode — and hides the choice behind a single internal AgentBackend interface. Swapping local for remote is a one-line change in the main process; the renderer never knows the difference.

The agent should live next to the files. The GUI should not.

ii. SDK vs RPC mode

Pi exposes the same underlying engine through two programmatic surfaces. They are not competing products — they are two transports for the same agent.

iii. Decision

Adopt both backends, behind a single internal interface.

Rationale

For local work, the SDK is the right primitive. Electron's main process is Node.js — there is no reason to spawn a subprocess and parse JSON when we can import a typed library directly. The SDK gives us custom tools (essential for integrating with native Electron dialogs and the renderer), direct state access, and event callbacks without serialization overhead.

For remote work, RPC over SSH is the right primitive. SSH already gives us a stdin and a stdout to a remote process, with authentication, encryption, and reconnection semantics solved. Pi's RPC protocol is designed for exactly this: JSON commands in, JSON events out, line-delimited. Writing our own remote agent transport on top of the SDK would, in practice, reinvent RPC mode.

The seam is an internal TypeScript interface named AgentBackend. Both implementations conform to it; the main process holds one instance; the renderer talks only to the main process. Adding a third backend later — Docker container, WSL, remote sandbox — is a localized change.

iv. Architecture

The Electron app at the top holds the abstraction. Underneath, two implementations carry out the work — one in-process, one across the network.

How data flows

The renderer sends a user prompt over Electron IPC. The main process invokes backend.prompt(...) on whichever AgentBackend is currently active. The backend executes — either by calling into the in-process AgentSession, or by writing a JSON line to a subprocess's stdin. Events come back as native callbacks (SDK) or parsed JSON lines (RPC), get normalized to a common AgentEvent shape, and are forwarded to the renderer over IPC.

v. Components

  • Renderer
    Chrome process running the UI. Receives normalized AgentEvents, sends prompts and user actions back via IPC. Has no knowledge of which backend is active.
  • Main process
    Node.js process. Owns the active AgentBackend, brokers IPC, holds any state that must survive renderer reloads.
  • AgentBackend
    Internal TypeScript interface. Defines the contract the main process depends on. Two implementations conform to it today; more may be added.
  • LocalSdkBackend
    Wraps an AgentSession from the Pi SDK. Imports tools and custom extensions from Electron-side code. Fast path; no serialization.
  • RpcBackend
    Spawns pi --mode rpc as a child process. Translates the AgentBackend method calls to JSON commands; parses JSON events back into the common shape. Works identically whether the subprocess is local or wrapped in SSH.
  • SSH transport
    Not a component we write — just the command we invoke. ssh user@host pi --mode rpc gives the RpcBackend a stdin and stdout that happen to lead to a remote process. Authentication, encryption, and connection lifecycle are SSH's responsibility.
  • pi (remote)
    The Pi binary running on the remote machine. Uses its own local tools to operate on remote files. Knows nothing about the network or the GUI.
  • Remote filesystem
    The actual code under edit. The agent sits next to it; only events, prompts, and tool results cross the wire.

vi. The AgentBackend interface

The contract is intentionally narrow. Anything the renderer cannot live without is here; everything else stays inside the backend implementation.

// packages/electron/src/agent/backend.ts

export interface AgentBackend {
  // Prompting
  prompt(text: string, options?: PromptOptions): Promise<void>;
  steer(text: string): Promise<void>;
  followUp(text: string): Promise<void>;
  abort(): Promise<void>;

  // Event stream — returns an unsubscribe function
  subscribe(listener: (event: AgentEvent) => void): () => void;

  // State
  getState(): Promise<AgentState>;
  getMessages(): Promise<AgentMessage[]>;

  // Model control
  setModel(provider: string, modelId: string): Promise<void>;
  setThinkingLevel(level: ThinkingLevel): Promise<void>;

  // Sessions
  newSession(): Promise<void>;
  switchSession(path: string): Promise<void>;
  fork(entryId: string): Promise<void>;

  // Lifecycle
  dispose(): Promise<void>;
}

Switching backends

Selecting which backend to use happens once, at session start, in the main process:

// packages/electron/src/agent/factory.ts

export async function createBackend(
  config: AgentBackendConfig
): Promise<AgentBackend> {
  switch (config.kind) {
    case "local-sdk":
      return new LocalSdkBackend({ cwd: config.cwd });

    case "rpc-local":
      return new RpcBackend({
        spawn: { command: "pi", args: ["--mode", "rpc"] },
      });

    case "rpc-ssh":
      return new RpcBackend({
        spawn: {
          command: "ssh",
          args: [config.host, "pi", "--mode", "rpc"],
        },
      });
  }
}

vii. Implementation phases

Each phase produces a runnable artifact. We do not start phase N+1 until phase N is shippable on its own.

  1. Electron skeleton and IPC contract

    Set up the Electron shell, the renderer framework, and the typed IPC layer. Define the AgentEvent and AgentCommand shapes that the renderer will consume — these are the same regardless of backend.

  2. Define the AgentBackend interface

    Write the TypeScript interface. Build a MockBackend that emits canned events so the renderer can be developed against it. No real agent yet.

  3. LocalSdkBackend — happy path

    Implement LocalSdkBackend by wrapping AgentSession from @earendil-works/pi-coding-agent. Ship a working local-only app: it should be useful at this point.

  4. Custom tools bridging to Electron

    Add custom tools (defined inline via defineTool()) that interact with the Electron app: native file picker, in-renderer diff viewer, confirmation dialogs. These are SDK-only and will not cross the SSH boundary.

  5. RpcBackend against local subprocess

    Implement RpcBackend; verify it against a locally-spawned pi --mode rpc. Strict line framing on \n only — do not use readline. Confirm parity with the SDK backend for all interface methods.

  6. Extension UI sub-protocol

    Implement the extension_ui_request / extension_ui_response protocol. This is what lets remote extensions show select, confirm, input, and editor dialogs through our UI when no local Electron context exists.

  7. Remote: SSH transport

    Wire RpcBackend to spawn ssh host pi --mode rpc. Handle key prompts, host key verification, reconnect on broken pipe, and surface connection state to the renderer. Test on at least one cloud VM and one bastion-hopped target.

  8. Workspace switcher

    UI to manage saved workspaces (local cwd or remote host + cwd). Per-workspace session history. Make the local/remote distinction visible but boring.

viii. Operational foundations

The architecture describes a buildable system. These are the substrate concerns that determine whether it ships and stays shipped — the foundation everything else assumes is present, and the things that are painful to retrofit.

  • Electron security
    nodeIntegration: false, contextIsolation: true, sandbox: true on every BrowserWindow. The renderer talks to the main process only through a typed preload.ts exposing verbs (prompt, abort) via contextBridge.exposeInMainWorld — never capabilities (fs, child_process). Add a strict CSP. Pi can read and write files; if a hostile page ever rendered in your window, you do not want it driving the agent.
  • Process lifecycle
    Define the shutdown sequence: abort current operation → drain in-flight events → dispose backend → confirm subprocess exit. Each entry point (window close, renderer crash, main exit, OS signal) routes into the same sequence. Orphaned pi --mode rpc processes on remote machines are a real failure mode and very difficult to debug after the fact.
  • Stream backpressure
    Pi streams tokens fast. Forwarding every text_delta raw via webContents.send() will lock up the renderer's main thread on a long response. Batch deltas in ~16ms windows or every N characters, and drain via requestAnimationFrame on the renderer. The IPC channel is not the bottleneck; React reconciliation is.
  • IPC contract
    Channels are typed end-to-end — either electron-trpc or a small hand-rolled wrapper with shared TypeScript types. Define them alongside AgentBackend so the renderer and main process evolve together. Untyped IPC is fine for a prototype and miserable for anything larger.
  • State ownership
    Main process is the source of truth for message history and session state. The renderer caches for performance and re-hydrates on reload. Persist in app.getPath('userData') via electron-store or a small JSON file. Do not put anything you care about in localStorage.
  • Auth and API keys
    Pi reads credentials from ~/.pi/agent/auth.json and environment variables. In RPC-over-SSH mode those must exist on the remote box, not the user's laptop. Pick a policy — in-UI paste forwarded via setRuntimeApiKey, env injection at spawn time, or out-of-band setup — and document it. Never log keys, never put them in URLs, never serialize them to session files.
  • Logging and diagnostics
    Rotating log file in userData/logs/. Capture Pi's full event stream at a configurable level. Ship a "Copy diagnostics" button in the UI. The single biggest predictor of whether you can confidently update your app is whether you can debug a failure you cannot reproduce locally.

ix. UX decisions to make

Questions the architecture cannot answer. Each looks small; each compounds across the product. They need designer and product input, not just engineering — but they need it early, because every later decision references whatever you chose here.

  • Tool execution display
    Pi streams tool_execution_update events with partial output as a tool runs. Live console pane? Collapsed by default? Truncated with click-to-expand? Whatever you decide, every tool the agent calls inherits it.
  • Thinking display
    For models with reasoning, thinking_delta events stream alongside the response. Inline? Behind a "Show thinking" toggle? Hidden by default? This sets the perceived character of the product more than almost any other choice.
  • Permission prompts
    Pi extensions raise select, confirm, input, and editor dialogs through the Extension UI sub-protocol. Native Electron dialogs or custom in-renderer modals? They have to look trustworthy and they must not be spoofable by agent output that happens to render HTML.
  • Edit approval
    The agent calls edit and write. Auto-apply? Show a diff and require approval per file? Approve once per session? Different products land in different places — Cursor approves silently, Aider asks per change, Claude Code has explicit modes. Pick a default, make it configurable, surface the choice prominently.
  • Session resumption
    The user closes the app and reopens it tomorrow. Last workspace? Last session in that workspace? An empty state with a "resume" affordance? Easy to defer; surprisingly hard to retrofit once users have built habits around whatever ships.

xi. Technology choices

The plan has stayed framework-agnostic up to this point on purpose — the architecture and visual language don't depend on the implementation language. This section names the picks: what the production codebase is built in, what supports it, and what to deliberately avoid. Technology decisions are most expensive when they get made implicitly, by whoever opens an editor first.

The core stack

  • React 18 + TypeScript
    The renderer. Three reasons over the alternatives: the design prototype from §x is already React, so engineers can use it as a direct visual reference and copy patterns verbatim; Electron + React is the well-trodden path (VS Code, Slack, Cursor, Linear's desktop client all live here), so tooling and recipes exist for every problem; the Pi SDK is TypeScript-first, and the renderer will consume dozens of typed event, message, and tool shapes from it. React's TypeScript story is mature and frictionless.
  • Electron 30+
    The shell. Section iii already committed to this implicitly — this is just naming a version floor. Track recent stable, not an old LTS; security patches matter and the Node version inside Electron is what your code runs against.
  • Vite + electron-vite
    The build. Fast HMR for the renderer, sensible defaults for the main and preload processes. Avoid webpack-based configurations unless there is a specific reason — the iteration loop matters every day, the bundle output only at ship time.
  • Zustand
    State. The agent's event stream needs careful, performant state management — React Context alone fragments and re-renders too aggressively at this scale, Redux Toolkit adds boilerplate the codebase doesn't earn. Zustand is the right size: a few well-named stores, no reducers, no boilerplate, easy to test.
  • CSS variables + CSS modules
    Styling. The design system from §x is already token-based; CSS modules consume those tokens directly with zero runtime overhead. Tailwind is acceptable if the team prefers it; the tokens still drive theming. What matters is that the accent / theme / density tweaks panel from §x writes CSS variables on :root and everything downstream picks them up automatically.

Supporting libraries

  • Radix UI primitives
    Headless components for menus, dialogs, tooltips, popovers, command palette. Behaviour and accessibility are theirs; visual design stays ours.
  • Lucide React
    Icon set. Clean line icons, MIT-licensed, matches the prototype's spirit. Tree-shakes well.
  • React Hook Form
    Forms. Only when settings or workspace configuration get complex enough to need it. The early settings screen can use plain controlled inputs.
  • Vitest
    Unit and integration tests (§xiii). Same toolchain family as Vite, substantially faster than Jest for our workload, and the migration cost on new code is zero.
  • Playwright
    End-to-end tests. The §xiii e2e layer, driving the real Electron app against a real Pi subprocess and (for the remote-mode tests) an in-container sshd.
  • electron-builder
    Packaging, code signing, and auto-update. Already named in §xii — repeated here so the production stack is in one place.

What not to use

Naming these explicitly is half the work — otherwise someone quietly adds one, a small refactor becomes a large one, and arguing it out later costs more than picking it now.

Next.js, Remix, or any server-rendering framework.
We're shipping a desktop app, not a website. SSR, routing-as-filesystem, and edge runtimes add concepts the product doesn't need and friction the team will pay for daily.
Component kits: Material UI, Chakra, Mantine, Ant Design, shadcn/ui.
Each imposes a visual system. We have one. The cost of fighting an opinionated kit's defaults is higher than the cost of building primitives from Radix + CSS modules.
CSS-in-JS runtimes: Emotion, styled-components, vanilla-extract (runtime mode).
Boot overhead, fights the token system, hard to inspect in DevTools, and the theming features they advertise are already covered by CSS variables. Build-time CSS-in-JS (vanilla-extract in zero-runtime mode, linaria) is fine if anyone insists.
Redux Toolkit, MobX.
The state surface isn't large enough to earn the boilerplate. Zustand covers the same ground in a fraction of the code. Reconsider only if state genuinely outgrows it — which is unlikely for a session-scoped chat product.
Jest.
Vitest is faster, shares config with the build, and reports stack traces against original TypeScript. There is no reason to choose Jest for a Vite project.

Alternatives worth a half-day spike

Most of the picks above are defensible against their alternatives without further investigation. Tauri is the one exception that warrants genuine consideration over Electron.

Tauri uses the operating system's native webview instead of bundling Chromium. Installed size drops from ~150 MB to ~15–50 MB. Memory footprint drops proportionally. The native feel — particularly on macOS — improves noticeably.

The cost is the IPC model. Tauri's commands live on the Rust side; Pi's SDK is a Node library. To use Pi with Tauri you would run a Node sidecar process and bridge to it — which is essentially the RpcBackend path from §iv, used even for local work. That removes the in-process advantage of the SDK backend but does not break the architecture. Two engineering days, including a real round-trip of Pi events end-to-end, is enough to decide.

If installer size and memory footprint matter to your users, do the Tauri spike before committing to Electron. If they don't, ship on Electron and don't look back.

Vue and Svelte are not on this list. Both are excellent frameworks; neither would be wrong here. What pushes us to React specifically is the design prototype already being React and the prior-art density of Electron + React in adjacent products. A team with deep Vue or Svelte expertise should not switch to React just to follow this plan — they should adopt the visual system from §x, the architecture from §iv, and write the renderer in whatever framework lets them ship fastest.

xii. Build, ship, operate

What it takes for users to install the app, trust it, update it, and let you fix things when they break. Most teams underestimate this category — particularly anything involving certificates and CI signing.

  • Bundling
    electron-builder with asar: true and a careful files glob. Do not ship the entire monorepo. Native modules (anything compiled against Node's V8) must be rebuilt against Electron's Node version.
  • Code signing
    macOS requires an Apple Developer ID and notarization for Gatekeeper to stop warning users. Windows wants an EV certificate for SmartScreen. Approximate annual cost: ~$99 for Apple, ~$300+ for an EV cert. Set up in CI before the first public beta. Skipping this means users see warnings; many will not click through.
  • Auto-update
    electron-updater is the practical default. Squirrel.Mac, NSIS for Windows, AppImage for Linux. Decide a channel strategy (stable / beta / canary) before the first release — moving channels later is harder than picking them up front.
  • Pi binary distribution
    Two options: require Pi to be installed and on the user's $PATH, or bundle a copy of it. Bundling means you ship Pi updates with app updates and own its runtime requirements. For remote machines the question recurses — does the remote host have Pi installed at all?
  • Pi version compatibility
    Pin the Pi version you build against. On RPC subprocess startup, check the version Pi reports matches what your RpcBackend expects. On mismatch, surface a clear upgrade prompt rather than crashing later when an unrecognized event shape arrives.
  • Crash reporting
    Electron's crashReporter is built in. Sentry, Crashlytics, or a self-hosted endpoint behind it. Configure before you ship a single beta build — crashes you cannot see are not crashes you can fix.
  • Telemetry and privacy
    Coding agents see proprietary code. Default everything to opt-in. Document precisely what (if anything) leaves the machine. Ship a privacy page. Local-first earns trust; anything else has to be argued for explicitly in the UI.
  • Platform parity
    SSH behaves differently across operating systems. Windows ships OpenSSH but key paths, agent forwarding, and ~/.ssh/config parsing all have edge cases. Path separators bite constantly. Test on macOS, Windows, and Linux from week one — not before release.

xiii. Testing strategy

The agent is non-deterministic; traditional snapshot tests fail in odd ways. Three layers, each with a different fidelity-to-reality tradeoff.

  • Unit
    Each AgentBackend implementation tested against a mocked LLM. Verify the contract — events fire, queues queue, abort aborts, dispose cleans up. Fast and deterministic.
  • Integration
    Real model, real network. Assert event shape, not content — a tool was called, a message arrived, the session compacted. Not flaky once you stop asserting on exact text.
  • End-to-end
    Playwright driving the actual Electron app against a real Pi subprocess. At least one path must exercise an SSH connection — a local Docker container running sshd works fine in CI and catches most cross-machine bugs early.

The IPC boundary is the cleanest seam: renderer tests mock the backend entirely; backend tests do not need a renderer. Optimizing for that cut keeps test runtimes manageable as the surface area grows.

xiv. Recommended starting order

The architecture suggests a buildable system. This is the order to actually build it in, prioritized by what is hardest to retrofit and what most unblocks the next decision.

  1. Electron security baseline. Context isolation, sandboxed renderer, typed preload, CSP. The only items on this list you cannot easily change later without a security review.

  2. The AgentBackend interface and a MockBackend. Design the contract before either real implementation. Build the entire renderer against the mock — the renderer team can move while the backend work proceeds in parallel.

  3. LocalSdkBackend with one model. Ship a working local-only app to yourself and one teammate. Most product decisions become legible only once something actually works.

  4. Logging, diagnostics, and crash reporting. Before real users, not after. The first user bug you cannot reproduce will teach you why this belongs early.

  5. Code signing pipeline in CI. Set up once, ignore for years. Required before any public beta. Trying to add this under release pressure is its own special kind of bad week.

  6. RPC backend against a local subprocess. Verify protocol parity with the SDK backend — every interface method should produce equivalent results through either path. No SSH yet.

  7. SSH transport. Now that everything else works.

The architecture is the easy part. The substrate is where most teams discover, two months in, what they should have built first.

xv. Risks and open questions

Custom tools do not cross SSH.
Tools defined inline with defineTool() only work in the SDK backend. For remote workspaces we either (a) ship those tools as on-disk extensions on the remote host, or (b) route them back to the GUI through the Extension UI sub-protocol. Decide per tool; document the contract.
Stdio framing is strict.
Pi's RPC mode splits records on \n only — Node's readline also splits on U+2028 / U+2029, which are legal inside JSON strings. We must use a manual buffer-and-split reader.
SSH connection lifecycle.
The agent process dies when the SSH connection drops. We need a clear UX for: lost connection mid-stream, key authentication prompts, hung subprocess, and resuming a session whose persisted file lives on the remote box.
Streaming latency over two hops.
Tokens travel: remote pi → SSH → main process → IPC → renderer. Each hop adds milliseconds. Should be unproblematic for chat-scale streaming; measure on a real long-haul connection before declaring done.
Where do sessions live?
Pi persists sessions as JSONL files next to the agent. For remote workspaces, sessions live on the remote machine. Listing, switching, and forking must work the same way in both modes — likely via the existing switch_session / fork RPC commands.
Auth storage and API keys.
The SDK reads keys from ~/.pi/agent/auth.json or environment variables. In RPC-over-SSH mode, those keys must exist on the remote machine, not the local one — or be injected per-session. Decide policy before shipping remote support.
