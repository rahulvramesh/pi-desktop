Kanban boards for projects & chats

Give every project a board where its chats are cards with a status, and roll all projects up into one cross-project board. A second lens on the data we already have in SQLite — not a new entity. This is a proposal: thinking, the impact surface, a build order, and the decisions that need an answer before code.

The idea, and why it fits

motivation

The app already models projects (folders the user added) that contain chats (pi agent sessions). Today chats are only ever shown as a recency-sorted list in the sidebar. But a chat is a unit of work — “understand the project”, “add a dev mode”, “fix the loader”. A Kanban view re-groups the same chats by status instead of by time, so the sidebar answers “what did I do recently” and the board answers “what’s in flight, what’s blocked, what’s done”.

Why it's cheap

Leverages what exists
  • Cards = existing chats. No new entity, no new persistence story.
  • One new nullable column on chats; everything else is read paths.
  • SQLite + typed IPC + zustand store are already the spine — we extend, not invent.
  • Run-state already streams, so “In progress” can be automatic.

Why it's worth it

What the user gets
  • A real sense of state across many parallel coding tasks.
  • Cross-project visibility: one board for everything you’re running.
  • “Blocked” / “Review” columns make hand-offs and waiting explicit.
  • Natural home for future per-card metadata (model, tokens, last activity).

Concept — two boards, one model

UX shape

A per-project board opened from a project (its chats only), and a global board reachable from a top-level sidebar entry that aggregates every project’s chats with a project chip on each card. Same columns, same card, different scope and a project filter on the global one.

Status columns are fixed; cards are chats. The per-project board drops the swimlanes and shows one project; the global board keeps them (or filters to one project).

What a card is, and the columns

taxonomy

A card is a chat (no separate “task” entity — that would split the model and double the bookkeeping). Every chat carries a status; new chats default to Todo. The recommended column set is deliberately small — five is already at the edge of useful for a single user:

Todo In progress Review Done Blocked

ColumnMeansEnters by
TodoCreated, not started.default on create
In progressActively being worked / agent running.auto on first run · or drag
ReviewAgent done; user is verifying the change.drag (manual)
DoneAccepted / shipped.drag (manual)
BlockedWaiting on input/decision/dependency.drag (manual)

Recommendation: ship todo · doing · done first (covers 90% of value), treat review and blocked as enabled-by-default but easy to collapse. An archived state is better as a boolean filter than a sixth column. Status is an enum string, stored lowercase.

Data model & the SQLite migration

main · db.ts

One additive change to the chats table. The catch: db.ts creates schema with CREATE TABLE IF NOT EXISTS and has no migration framework, so an existing user’s DB won’t get the new column from the create statement alone. We need a tiny idempotent migration on open.

Schema delta

chats — one column
  • status TEXT NOT NULL DEFAULT 'todo'
  • Optional later: status_changed_at INTEGER for “age in column”.
  • Index (project_id, status) for fast per-project board reads.

Migration shape

idempotent, runs on DB open
  • Read PRAGMA table_info(chats); if status absent, ALTER TABLE chats ADD COLUMN status TEXT NOT NULL DEFAULT 'todo'.
  • Existing rows backfill to todo via the column default.
  • Wrap in a user_version bump so it’s a known pattern for the next migration too.

Repository & types

  • chatsRepo gains setStatus(id, status) and includes status in the row mapper; list() already returns full rows so the board reads come free.
  • Chat in src/shared/ipc.ts gains status: ChatStatus where ChatStatus = 'todo' | 'doing' | 'review' | 'done' | 'blocked'.
  • No change to session_file/transcript handling — status is orthogonal to agent state.

Auto-transition from agent run state

non-destructive

The agent run-state (idle · thinking · running · queued) is transient and already streams to the renderer; board status is persistent. They are different axes — keep them separate, but let run-state nudge status so the board stays honest without manual fiddling. Rules are intentionally minimal and never override an explicit user decision:

  • Todo → In progress automatically the first time a chat’s agent runs (run-state leaves idle).
  • No auto-move out of Done or Blocked — those are user judgments.
  • Never auto-Done. “Agent finished” ≠ “work accepted”. Completion stays a manual drag (optionally suggest Review on agent_end).
  • A running chat shows a live indicator on its card (reuse the existing Soft Cells loader) regardless of column.

Net: you create a chat (Todo), send a prompt (auto → In progress, card pulses), and you decide when it’s Review/Done/Blocked. One automatic edge, everything else explicit.

Drag & drop

No DnD library is in package.json. For a single-user, few-dozen-card board, native HTML5 drag events (draggable + dragover/drop) are enough and add zero dependencies — recommended first cut. A keyboard fallback (move-to-column menu on the card) covers accessibility without a library.

The global (cross-project) board

scope & scale

Same columns; cards span all projects, each tagged with a project chip and color. Two viable layouts — recommend columns with project swimlanes (rows per project inside each status column) because it preserves the “by project” mental model while still reading status left-to-right. A project filter collapses it to one project (which equals the per-project board — so the per-project board can be literally the global board pre-filtered).

Recommended

Status columns × project swimlanes

One render path. Per-project = global with a fixed project filter. Less code, consistent behavior.

Scale note

Stays simple for now

Chats are low-volume per user. If a board ever exceeds a few hundred cards, add windowing — specified, not needed at current scale.

smallest shippable first

Each step is independently shippable and verifiable; later steps are additive.

Todo→In progress on first run; Soft Cells pulse on running cards. Non-destructive guards.

Risks & tradeoffs

watch list
  • Migration on existing DBs. The CREATE TABLE IF NOT EXISTS pattern won’t add the column for existing users — the PRAGMA-guarded ALTER is mandatory, not optional, or older installs break on read.
  • Run-state vs. status confusion. They look similar (“in progress”). Keep wording distinct (status = column, run-state = the pulse) and never let one silently rewrite the other beyond the single Todo→Doing edge.
  • Status drift. Without auto-Done, cards rot in In progress. Mitigate with a gentle “suggest Review” on agent_end, not a forced move.
  • Scope creep into a task manager. Resist sub-tasks, assignees, due dates — this is a single-user lens on chats, not Jira. Keep the column set frozen at five.
  • Sidebar vs. board duplication. Two ways to see chats. Keep the sidebar as the recency/last-touched list; the board owns status. Don’t reorder the sidebar by status.

Open questions — decide before coding

needs your call
1 · Card unit: chats, or a separate task entity?
Recommendation: chats. A separate task entity doubles persistence and the user’s mental model for little gain at single-user scale. Confirm.
2 · Column set: 3 (todo/doing/done) or 5 (+review/blocked)?
Recommendation: ship 3, enable 5 by default with the extras collapsible. Your call on whether blocked earns a column vs. a card flag.
3 · Where does the global board live?
A new top-level sidebar entry (a real one, replacing/【beside the “Automations” stub), or a tab in the right Inspector pane? Recommendation: top-level view — it spans projects, the Inspector is project/chat-scoped.
4 · Auto-transitions: just Todo→In progress, or also suggest Review on finish?
Recommendation: auto Todo→In progress only; a dismissible “move to Review?” hint on agent_end. No automatic Done, ever.
5 · Drag&drop: native HTML5 (no dep) or a small DnD lib?
Recommendation: native first — zero dependencies, enough for this scale; revisit only if multi-select/animated reordering is wanted.
